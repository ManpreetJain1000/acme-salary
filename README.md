# ACME Salary Manager

[![CI](https://github.com/ManpreetJain1000/acme-salary/actions/workflows/ci.yml/badge.svg)](https://github.com/ManpreetJain1000/acme-salary/actions/workflows/ci.yml)

Web software for ACME's HR manager to **maintain salary data for 10,000 employees across 10 countries** and **answer questions about how the organisation pays people**, replacing a spreadsheet workflow.

## What it answers
1. *Find employee X and update their salary.* Directory with debounced search and filters, plus an edit drawer.
2. *What do we pay a Senior Engineer in India vs Germany?* Pay bands (min / p25 / median / p75 / max) per role × country, compared in USD.
3. *Where does payroll go?* Headcount and USD-normalised payroll by country and department.
4. *Who is paid unusually high or low for their role?* Outliers relative to the median of the same title in the same country.
5. *When did this salary change?* An immutable salary history per employee.

## Quick start

Requires Node 20+.

```bash
npm install
npm run dev      # API on :4000 (seeds 10k employees on first boot), web on :3000
```

Open http://localhost:3000 and sign in with the demo account shown on the login page (**hr@acme.example** / **acme-demo-2026**). Development needs no configuration; production requires `HR_PASSWORD` and `SESSION_SECRET` (see `.env.example`).

| Command | What it does |
|---|---|
| `npm test` | All tests: API (unit + integration, in-memory SQLite) and web helpers, ~5 s |
| `npm run seed` | Seed if empty; `npm run seed -- --reset` to wipe and reseed (refused in production unless `ALLOW_RESET=true`) |
| `npm run bench --workspace api` | Benchmark hot paths on the 10k seed; `BENCH_COUNT=100000` for a scale test |
| `npm run backup --workspace api` | Consistent, integrity-checked copy of the live database (keeps the newest 14) |
| `docker build -t acme-salary .` then `docker run -p 3000:3000 -e HR_PASSWORD=acme-demo-2026 -e SESSION_SECRET=$(openssl rand -hex 32) -e COOKIE_SECURE=false -e DEMO_LOGIN_HINT=true acme-salary` | Production image locally (plain HTTP, hence `COOKIE_SECURE=false`) |

## Deploy
The repo is one Docker image: Next.js is public and proxies `/api` to the API on an internal port.
- **Render:** New → Blueprint → pick this repo (`render.yaml`: demo password shown on the login page, session secret generated by Render).
- **Railway / Fly / any Docker host:** deploy the `Dockerfile`; the platform's `PORT` is respected.

The database is seeded deterministically on first boot. On free tiers with ephemeral disks, edits reset on redeploy. Mount a volume at `/app/data` to keep them, and schedule `node apps/api/dist/db/backup-cli.js` (or run Litestream) to copy backups off the machine.

## Stack and why
- **API:** Node + TypeScript, Express 5, `better-sqlite3`, zod. A small, explicit stack with synchronous transactions.
- **DB:** SQLite (WAL) with versioned migrations. Right-sized for 10k rows; all application SQL sits in one repository layer (enforced by a test), so services and routes don't change for Postgres.
- **UI:** Next.js (App Router) + Mantine + React Query + Mantine Charts.
- **Tests:** Vitest + Supertest, deterministic, no network, fixed clock and seed.

## Engineering highlights
- **Money is integer minor units** in the employee's local currency. USD is derived at read time from a dated static FX table and never stored over the original.
- **The salary audit trail can't be lost:** every change writes history in the same transaction, people who leave are terminated (not deleted), and database triggers reject any edit or delete of history.
- **Seed:** a seeded PRNG and fixed reference date (same data everywhere); one `BEGIN IMMEDIATE` transaction (all or nothing); the emptiness check runs inside the transaction, so concurrent boots can't double-seed. 10k employees in under a second.
- **Measured at 10× scale (100k employees):** every directory query under 20 ms, search 9 ms, a cached insights page 0.1 ms. Getting there took an insights cache keyed by a database-maintained data version, an expression index for the USD salary sort, an FTS5 trigram search index, and fresh planner statistics. Query-plan tests guard against regressions ([performance](docs/performance.md)).
- **Sign-in:** scrypt-hashed password, HMAC-signed HttpOnly + SameSite session cookie (Secure in production), every API route protected (sweep-tested), failed sign-ins rate limited, POSTs must be JSON (CSRF defence in depth), production won't boot without real secrets.
- **Operations:** a request id on every response and in one JSON log line per request (no query strings: search terms are names), per-client rate limiting that works behind the proxy, online backups with integrity check and retention.
- **Security hygiene:**
  - zod validation on every input;
  - parameterised SQL only;
  - allow-listed sort fields;
  - LIKE wildcards escaped;
  - page size capped at 100;
  - helmet headers, 50 kb JSON limit, API not publicly exposed;
  - no stack traces or salary data in errors or logs.
- **Every screen has loading, empty and error states.**

## Deliberately out of scope
Multi-user accounts and SSO (one HR sign-in today), payroll/tax, live FX, Excel import/export (the highest-value next feature), demographic pay-gap analysis, and horizontal scaling (needs Postgres; the path is documented). Reasons are in [requirements](docs/requirements.md) and [decisions](docs/decisions.md).

## What I'd do next
1. SSO with per-user accounts and roles, salary fields gated by role, and an access audit log.
2. Excel/CSV import with a dry-run diff, plus export of any filtered view.
3. Postgres behind the existing repository layer, migrations as a release step, then several stateless instances with a shared rate-limit store.
4. Precomputed insights aggregates, so the first visit after a change is fast at 100k+ too.
5. Scheduled FX refresh, with historical rates per salary change.
